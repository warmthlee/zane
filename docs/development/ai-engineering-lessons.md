# AI 工程长期复用手册

## 1. 目标与适用范围

这份文档不是一次性总结，而是面向长期使用的工程规范。它适用于：
- 基于 AI 协作的个人或团队项目
- 需要在多 Agent 工具之间切换的工程实践
- 需要记录上下文、任务状态和发布过程的项目

它的核心目的，是把“AI 生成代码”从短期效率工具，升级成可以稳定迭代、可回溯、可维护的工程方法。

## 2. 最核心的原则：先定义边界，再做执行

AI 非常适合加速执行，但最容易出问题的地方，是“需求范围悄悄扩展”。

因此，任何任务都必须提前明确：
- 做什么
- 不做什么
- 谁负责业务判断
- 任务如何被验收
- 什么时候结束

如果没有这些约束，AI 往往会在“看起来像能工作”的方向上继续生成内容，而不是在真正解决问题的边界内推进。

## 3. 一套稳定的协作范式

### 3.1 任务必须小而清晰

每个任务应尽量具备：
- 明确输入
- 明确输出
- 明确验收标准
- 明确风险边界

不要让一次任务变成“顺手做多个功能”的大包。大任务必须拆成小任务，并让每个小任务都能单独验证。

### 3.2 任务必须有验收清单

每个任务完成前，都必须回答：
- 代码是否已落地
- 是否符合需求边界
- 是否通过构建、测试、lint 或目标检查
- 是否有副作用需要记录
- 是否更新了相关文档

这件事比“代码看起来不错”更重要，因为工程中的真正风险，通常不在代码写法，而在“没有被验证”的改动。

### 3.3 任务必须保留项目记忆

代码、文档和归档文件应当一起构成项目长期记忆。AI 会话可以帮助执行，但不能替代项目事实来源。

在实践中，必须保留：
- 需求背景
- 决策理由
- 关键改动
- 验收方式
- 发布记录
- 回滚信息

这让项目在切换 Agent 工具时，仍然保持可恢复状态。

## 4. AI 适合做什么，不适合做什么

### AI 适合做的事
- 代码生成和结构整理
- 文档草稿与目录设计
- 任务拆解和实现方案
- 重复脚本与检查流程
- 发布前验证与变更说明
- 代码风格整理和命名重构

### AI 不适合替代的事
- 产品方向裁定
- 目标优先级决策
- 发布最终确认
- 风险判断和边界管理
- 需要真实业务理解的设计取舍

一句话总结：AI 擅长“加速执行”，但不能替代“人类判断价值与边界”。

## 5. 工程设施比功能更重要

在 AI 协作场景中，真正决定项目是否能长期推进的，往往不是某个页面功能，而是：
- 项目命令是否统一
- 文档是否持续更新
- 会话是否可归档
- 发布是否可重复验证
- 回滚是否可执行

这也是为什么本项目会保留：
- 统一 Agent 工作流
- 多 Agent 兼容协议
- 结构化会话存档
- 最小发布/回滚闭环

这些内容的价值，不在“看起来高级”，而在于项目在未来继续迭代时，不会因为上下文丢失而停摆。

## 6. 这项目的实际实践要点

### 6.1 Tool agnostic

项目以“适配多种 Agent 工具”为目标，不绑定单一 AI 系统。这样做的好处是：
- 更容易切换 Claude Code / Codex / Copilot 等工具
- 不依赖某一工具的记忆特性
- 更容易持续维护与复用

### 6.2 代码与文档并重

文档不是附属品，而是工程资产。每个实现阶段都应记录：
- 任务目标
- 范围说明
- 关键决策
- 验收方式
- 风险和后续事项

### 6.3 结构化会话归档

本项目保留了会话归档机制，核心目标是：
- 让 AI 任务可恢复
- 让上下文可追溯
- 让跨设备、跨会话连续工作成为可能

### 6.4 发布流程必须审核

部署不应只靠“脚本跑起来”。真正可靠的发布流程包括：
- 构建
- lint / 检查
- 发布前确认
- 发布后状态核对
- 回滚准备

## 7. 面向未来的工程判断

未来成熟项目的核心能力，不是“AI 生成多少代码”，而是：
- 可切换工具
- 可回溯历史
- 可持续验证
- 能安全发布
- 能沉淀知识

这也是本项目从一开始就强调：
- 明确边界
- 文档优先
- 任务可验收
- session 可保存
- 运维可执行

## 8. 结论

AI 编程的真正价值，不是把工作交给机器完成，而是让人类把更多精力放在：
- 目标设计
- 产品判断
- 代码边界
- 发布确认
- 长期演进

而执行层面的重复劳动，则交给 AI 去做。这样才是稳定、可扩展和长期有效的 AI 协作方式。
