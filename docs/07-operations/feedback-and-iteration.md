# 反馈与迭代

## 反馈来源

| 来源 | 内容 | 处理方式 |
| --- | --- | --- |
| 自用观察 | 使用中的摩擦与缺失 | 直接进入 backlog |
| 读者反馈 | 错误、建议、内容请求 | 分类后评估 |
| 访问与工具数据 | 使用频率、错误率 | 用于优先级判断 |
| 外部工具变化 | API 变更、条款更新 | 适配器维护任务 |
| 事故复盘 | 根因与改进项 | 进入风险表或 backlog |

## 收集方式

- 页面提供轻量反馈入口（邮件或表单），不引入重型客服系统。
- 反馈记录包含：来源、场景、期望、优先级建议。
- 不要求用户提供无关个人信息。

## 进入 backlog

1. 去重：先检索 `../01-requirements/feature-backlog.md`。
2. 归类：缺陷 / 改进 / 新功能 / 维护。
3. 评估：价值、成本、风险、依赖。
4. 登记：分配 ID、优先级、状态。
5. 排期：进入当前阶段或后续阶段。

## 优先级原则

1. 数据安全与可用性优先。
2. 影响核心流程（记录、登录、同步）的缺陷优先。
3. 高频工具的小改进优先于低频新功能。
4. 新功能必须有明确使用场景，不为技术兴趣扩张。
5. 外部依赖维护与功能开发同样计入排期。

## MVP 迭代闭环

```text
想法 → 最小实现 → 上线 → 观察 → 决策
                              ├── 继续迭代
                              ├── 保持现状
                              └── 归档下线
```

- 每个 MVP 设定观察期与判断标准（使用量、完成率、维护成本）。
- 未达标准的 MVP 及时归档，避免长期维护负担。
- 下线需保留说明与数据导出。

## 复盘节奏

- 每个阶段结束：回顾目标、完成度、遗留问题。
- 每次事故：按模板复盘。
- 每季度：清理 backlog、归档低价值项、更新路线图。

## 指标回顾

关注趋势而非单点数字：

- 记录频率与复用情况。
- 工具使用分布与错误率。
- 同步成功率。
- 维护成本（发布耗时、故障次数）。
- 新 MVP 的验证结论。
