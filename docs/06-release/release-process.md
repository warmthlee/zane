# 发布流程

## 版本策略

- 使用语义化版本：`MAJOR.MINOR.PATCH`。
- 功能新增 → MINOR；修复 → PATCH；破坏性变更 → MAJOR。
- 单人项目可简化，但发布记录必须保留版本号与日期。

## 发布门禁

发布前必须全部通过：

1. 前端 `npm run build`。
2. 前端 `npm run lint`。
3. 后端 `dotnet build`。
4. 后端 `dotnet test`。
5. 关键页面手动检查。
6. 数据库迁移演练（如涉及）：本地执行 `npm run release:check`（临时空库上重复应用迁移，并检查模型无待生成迁移），或确认 CI `migration` job 通过；有新迁移时另在生产备份副本上演练一次。
7. 变更摘要与验收记录已写完。

任一项失败不得发布。

## 发布步骤

### 1. 准备

- [ ] 确认发布范围与版本号。
- [ ] 确认 `main` 干净且 CI 通过。
- [ ] 记录本次变更摘要。
- [ ] 确认回滚方案。

### 2. 数据

- [ ] 备份生产 SQLite。
- [ ] 在副本上执行 `dotnet ef database update`。
- [ ] 确认迁移耗时与锁影响可接受。
- [ ] 确认迁移可重复执行或有明确一次性说明。

### 3. 发布

1. 后端：从 `main` 的 CI `package` job 下载 `zane-api` artifact，按 `deployment.md` 更新服务进程（向后兼容）。
2. 备份数据库后用产物中的 `efbundle` 应用迁移。
3. 前端：push `main` 触发 `deploy.yml`，构建后 rsync 到 1Panel。
4. 先兼容后端再发前端，避免旧前端调用不存在接口。

### 4. 发布后

- [ ] 首页、记录、工具、聚合页可访问。
- [ ] 健康接口 `/api/v1/health` 返回正常。
- [ ] 写入接口仅在本机/内网可达（鉴权落地前）。
- [ ] 外部数据源失败时有降级。
- [ ] 日志无异常峰值。

### 5. 记录

- 更新 `../08-governance/changelog.md`。
- 记录发布摘要到 `.ai/` 归档（如使用脚本）。
- 标注遗留风险。

## 发布节奏

- 小步发布，避免攒大版本。
- 文档与配置变更可独立发布。
- 破坏性变更单独发布，并提前准备回滚。

## 审批

- 发布由负责人确认。
- AI 可以准备构建、检查与发布说明，但不能替代最终确认。
- 紧急修复可简化流程，但事后必须补记录。
